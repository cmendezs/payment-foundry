# Stripe

Index of Stripe reference material for the Engagement Manager. The presence of this file signals that Stripe is a supported PSP in this workspace.

## Product lines

| File | Covers |
|---|---|
| [`payments.md`](payments.md) | Payment Intents, Payment Methods, Charges, Refunds, Webhooks, and Payment Links (dashboard-first and API path, with and without Connect `on_behalf_of`). The core flow for accepting a payment. |
| [`products-and-prices.md`](products-and-prices.md) | Shared catalog primitives: `Product` (including `tax_code`), `Price` (recurring/one-time, `tax_behavior`, `currency_options`, `lookup_key`), tiered pricing. Consumed by Billing, Tax, and the API path of Payment Links. |
| [`platform.md`](platform.md) | Stripe Connect (Standard, Express, Custom accounts), transfers, payouts, platform fees. For marketplaces and platforms paying out to other parties. |
| [`terminal.md`](terminal.md) | Reader setup, connection tokens, in-person Payment Intents, offline mode. For physical point-of-sale. |
| [`issuing.md`](issuing.md) | Cardholder and card creation, spending controls, authorization webhooks, funding. For issuing cards to users. |
| [`treasury.md`](treasury.md) | Embedded banking for platforms (financial accounts, inbound/outbound ACH and wires, ReceivedCredits/Debits, OutboundPayments/Transfers, reconciliation, Issuing pairing). Platform-integrator path only. |
| [`tax.md`](tax.md) | Stripe Tax: registrations, automatic tax calculation on Invoices and Checkout/Payment Links, Customer Tax IDs and reverse charge, marketplace facilitator handling under Connect, exports for filing. |
| [`capital.md`](capital.md) | Stripe Capital (platform model): eligibility surface, offer presentation and disclosures, application redirect, repayment mechanics, webhooks. Connect-coupled. |
| [`stablecoins.md`](stablecoins.md) | Canonical cross-cutting reference for Stripe's stablecoin surface: Optimized Checkout acceptance, Treasury stablecoin financial accounts (US), Issuing card spend from stablecoin balances, Open Issuance via Bridge. | [`crypto-onramp.md`](crypto-onramp.md) | Embeddable fiat-to-crypto purchase product for end users. Integration modes (no-code, embeddable, headless preview), KYC modes (including the lower-threshold $500 mode), Stripe as merchant of record, custom-stablecoin delivery via Open Issuance. |
| [`fraud-and-disputes.md`](fraud-and-disputes.md) | Radar fraud rules, Radar for Fraud Teams advanced capabilities (custom lists CRUD, advanced rule patterns, Risk Insights, reviews), 3D Secure enforcement, disputes/chargebacks. |
| [`reports.md`](reports.md) | Reporting API, Activity Report, Payout Reconciliation Report, IC+ pricing, payouts, Stripe Sigma. |
| [`billing.md`](billing.md) | Subscriptions, invoicing, pricing models (per-seat, usage-based), customer portal, dunning, tax-on-invoices cross-reference. For recurring billing. |
| [`testing-and-ops.md`](testing-and-ops.md) | Test/live mode practices, test data, webhook testing, load testing, error handling and rate limits, API versioning, support model. |

## When to load which file

- Almost every engagement needs `payments.md`, it covers the base payment flow that other product lines build on. Payment Links live in the same file as a Stripe-hosted alternative to the Payment Element.
- Load `products-and-prices.md` the first time any of Billing, Tax, or the API path of Payment Links is in scope. The catalog primitives are shared, so load this file once rather than re-deriving the catalog model from each consumer.
- Load `platform.md` if the team's use case involves a marketplace, platform, or any scenario where money needs to move to a third party (not just the business itself).
- Load `terminal.md` if any part of the use case involves in-person/card-present payments.
- Load `issuing.md` if the team needs to issue cards (virtual or physical) to users, employees, or customers.
- Load `treasury.md` if the team is a Connect platform offering embedded banking (financial accounts, ACH/wires, money movement) to its connected accounts. Treasury frequently pairs with `issuing.md` (Treasury as the funding source for Issuing cards) and always depends on `platform.md`. This is a heavyweight scope, confirm contract enablement and operational readiness with `head-of-payments`, `compliance-officer`, and `finance-treasury` before committing.
- Load `tax.md` when calculating, collecting, or reporting tax across jurisdictions is in scope. Tax can be implemented without Billing, but always loads `products-and-prices.md` alongside it (for `tax_code` and `tax_behavior`). Tax under Connect (marketplace facilitator) is one of the trickier areas, plan time for `compliance-officer` review.
- Load `capital.md` if the team is a Connect platform offering Stripe Capital financing to its connected accounts. Always depends on `platform.md`. Surface eligibility and disclosures with `compliance-officer` review before any seller sees an offer.
- Load `stablecoins.md` when stablecoins enter any of the in-scope consumer surfaces: acceptance via Optimized Checkout (cross-references in `payments.md`), recurring subscriptions (in `billing.md`), Treasury balances and on-chain payouts US-only (in `treasury.md`), or card spend from a stablecoin balance (in `issuing.md`). Open Issuance via Bridge is also scoped here. Outside counsel review is the bar for stablecoin work, not an option; flag this with `compliance-officer` and `head-of-payments` at scoping.
- Load `crypto-onramp.md` if the team is a Web3 platform, NFT marketplace, DeFi app, or crypto wallet that wants to let users buy crypto in-product, with Stripe as merchant of record. Standalone product line with no dependencies on other Stripe surfaces (custom-stablecoin delivery via Open Issuance does cross-reference `stablecoins.md`). Confirm regional availability and KYC-mode constraints early.
- Load `fraud-and-disputes.md` when fraud rules, authentication (3DS) enforcement, or dispute handling become the active topic, this often pairs with the `fraud-officer` and `security-officer` sub-agents. Radar for Fraud Teams (custom lists CRUD, advanced rule patterns, Risk Insights, full review workflow) is covered in this file as the higher tier of Radar; confirm the team is on the Fraud Teams SKU before designing flows that depend on it.
- Load `reports.md` when reporting, reconciliation, or finance/accounting integration becomes the active topic, this often pairs with the `finance-treasury` sub-agent.
- Load `billing.md` if the use case involves subscriptions, recurring billing, or usage-based pricing. If in scope, Billing typically slots in as its own step alongside or after core payments in the engagement sequence. Pair with `products-and-prices.md` for the catalog model, and `tax.md` when tax-on-invoices is needed.
- Load `testing-and-ops.md` when the team is setting up their test environment, preparing for go-live, or troubleshooting API errors/rate limits, this often pairs with the `solution-architect` sub-agent.

A single engagement can span multiple product lines (e.g., a marketplace platform using `payments.md`, `platform.md`, `tax.md`, and `treasury.md`). Load each relevant file as the engagement reaches that part of the sequence, do not load everything upfront.

## General notes

- All code examples in these files use Stripe's officially documented API patterns. Anything not certain is marked `[Unverified]` with a pointer to the relevant `stripe.com/docs` section, confirm against current docs before relying on it.
- Examples are shown primarily in Node.js (using the `stripe` npm package) with notes for other languages where the pattern differs meaningfully. Adapt to the team's actual stack, the underlying API calls and object model are the same across SDKs.
- Several product-line files flag specific decisions where a specialist sub-agent should weigh in (cross-referenced inline at the relevant section). Recurring examples: multi-capture/extended-authorization choice (`payments.md` -> `solution-architect`, `fraud-officer`), Payment Links vs. custom checkout (`payments.md` -> `solution-architect`, `frontend-developer`, `head-of-payments`), catalog and `tax_behavior` design (`products-and-prices.md` -> `backend-developer`, `finance-treasury`), unified vs. regional account structure (`platform.md` -> `solution-architect`, `finance-treasury`), SCA exemption strategy (`fraud-and-disputes.md` -> `compliance-officer`, `fraud-officer`), Radar for Fraud Teams custom-list lifecycle (`fraud-and-disputes.md` -> `fraud-officer`, `security-officer`, `compliance-officer`), card network monitoring program thresholds (`fraud-and-disputes.md` -> `fraud-officer`, `finance-treasury`), tax-nexus and marketplace-facilitator handling (`tax.md` -> `compliance-officer`, `finance-treasury`, `head-of-payments`), Capital offer presentation and combined repayment cash flow (`capital.md` -> `compliance-officer`, `finance-treasury`, `head-of-payments`), Treasury financial-account design and pending-vs.-final ledger model (`treasury.md` -> `head-of-payments`, `compliance-officer`, `finance-treasury`, `solution-architect`, `backend-developer`), stablecoin acceptance and dual-currency ledger design (`stablecoins.md` -> `head-of-payments`, `frontend-developer`, `finance-treasury`, `compliance-officer`, `backend-developer`), Open Issuance launch decision (`stablecoins.md` -> `head-of-payments`, `compliance-officer`, `finance-treasury`), Crypto Onramp integration mode and KYC-mode choice (`crypto-onramp.md` -> `solution-architect`, `frontend-developer`, `compliance-officer`), IC+ pricing eligibility (`reports.md` -> `finance-treasury`, `solution-architect`), billing migration (`billing.md` -> `backend-developer`, `finance-treasury`), and test clocks/`stripe-mock` adoption for CI (`testing-and-ops.md` -> `backend-developer`, `solution-architect`).

## Freshness and Verification

Each product-line file opens with a standard "Verification References" block. That block lists the canonical Stripe documentation URLs, the Stripe API Changelog, Stripe MCP query hints (when the MCP is connected), and the volatile items the team must re-verify before relying on the file (GA/beta status, header requirements, account-level capability gating, API version assumptions).

The `/validate-context` skill reads only those blocks and produces `outputs/<engagement>-context-validation.md` with `[Verified]`, `[Unverified]`, and `[Blocker]` items. Run it once per engagement, after `/start-session` and before the first implementation step. The validation output is consumed by `/wrap-up` and by each sub-agent at review time.

Where the team has connected the Stripe MCP server (see `setup/installation-guide.md`), `/validate-context` uses it to query the live API reference, the API Changelog, and the connected test account's actual capabilities. Where the MCP is not connected, `/validate-context` falls back to `WebFetch` against the canonical URLs declared in each Verification References block.
