## ما هذا المشروع

معظم مساعدي البرمجة بالذكاء الاصطناعي يولّدون تكاملاً مع مزود خدمة الدفع (PSP) مباشرة من أمر واحد: نموذج دفع، ومعالج Webhooks، وانتهى الأمر. قد يعمل الكود، لكن القرارات الكامنة وراءه (نطاق PCI، قواعد الاحتيال، عملة التسوية، استراتيجية إعادة المحاولة) لم يتم اتخاذها فعلياً من قبل الأشخاص المسؤولين.

يقوم Payment Foundry بتنفيذ مشاركة منظمة بدلاً من ذلك. وكيل ذكاء اصطناعي على مستوى كبير (مدير المشاركة) يوجه فريقك التقني من تحديد النطاق إلى التنفيذ، ويجمع على طول الطريق متطلبات الأدوار التي ستتعايش مع النتيجة: الامتثال، مكافحة الاحتيال، الأمن، المالية، الواجهة الخلفية، الواجهة الأمامية، البنية المعمارية، ومسؤول المدفوعات.

جلسة واحدة. ثماني وجهات نظر. ملخص تنفيذ واحد يمكن لمهندسيك العمل بموجبه.

## ما الذي تحصل عليه

| القدرة | ما تفعله |
|---|---|
| مسار مشاركة منظم | يوجه فريقك عبر تحديد النطاق والمتطلبات والتنفيذ والمراجعة بترتيب ثابت ومنطقي |
| جمع متطلبات أصحاب المصلحة | يسجل قرارات وقيود كل دور في ملف مخصص مع تقدم الجلسة |
| أمثلة كود مرتكزة على مزود الدفع | كل مثال كود حقيقي وقابل للتشغيل، مكيّف من محتوى مرجعي موثق لمزود الدفع، وليس كوداً وهمياً أبداً |
| مراجعات المتخصصين | ثمانية وكلاء فرعيون يردون بـ موافقة أو تنبيه أو حظر، مع تبرير، عند نقاط القرار الحاسمة |
| ملخص التنفيذ | مُخرَج مكتوب واحد يغطي القرارات والكود والنقاط المفتوحة وكل ما هو غير موثق |
| قابل للتوسيع لمزودي دفع جدد | أضف مزود دفع جديد باتباع بنية `psps/<الاسم>/` الحالية، دون الحاجة لتغيير التعليمات الأساسية |

## كيف تسير الجلسة

```
/start-session
      |
      v
  النطاق والقيود  ->  متطلبات أصحاب المصلحة (دور واحد في كل مرة)
      |
      v
  /validate-context  ->  التحقق من المحتوى المرجعي لمزود الدفع مقابل المصادر الرسمية
      |
      v
  المدفوعات الأساسية -> Webhooks -> المنصة / الطرفية / إصدار البطاقات (حسب النطاق)
      |
      v
  مراجعات المتخصصين (موافقة / تنبيه / حظر)
      |
      v
/wrap-up  ->  الملخص + الدليل التفصيلي + قائمة التحقق للإطلاق (outputs/<engagement>/)
```

## البداية السريعة (أربع خطوات)

### 1. استنساخ المستودع والدخول إلى المجلد

```bash
git clone https://github.com/cmendezs/payment-foundry.git
cd payment-foundry
```

### 2. إعداد البيئة

```bash
cp .env.example .env
# افتح .env وأدخل مفاتيح Stripe الاختبارية
# راجع setup/environment-keys.md للتفاصيل
```

### 3. قراءة قائمة التحقق للجلسة الأولى

افتح `setup/first-session-checklist.md` وأكمله قبل جلستك الأولى. يستغرق حوالي عشر دقائق ويمنع أكثر مشاكل الإعداد شيوعاً.

### 4. الإطلاق وبدء المشاركة

```bash
claude
```

ثم في جلسة Claude Code:

```
/start-session
```

هل تستخدم Google Antigravity أو AWS Kiro أو Mistral Vibe بدلاً من ذلك؟ نفس المسار `/start-session` و `/validate-context` و `/wrap-up` متاح في كل منها، راجع `setup/other-agents.md` لخطوات الإطلاق المكافئة ومواقع المهارات.

## أوامر Slash

ثلاثة أوامر تغطي دورة حياة المشاركة بالكامل.

| الأمر | متى يُنفَّذ | ما يفعله |
|---|---|---|
| `/start-session` | في بداية كل مشاركة | يحدد مزود الدفع، يعرّف نطاق المشاركة، يجمع متطلبات أصحاب المصلحة دوراً بدور، ويقترح تسلسل التنفيذ |
| `/validate-context` | بعد `/start-session`، قبل بدء التنفيذ | يتحقق من الحقائق الخاصة بمزود الدفع ضمن النطاق (الحالة، التسعير، قيود القدرات، سلاسل الترويسات، إصدارات API) مقابل المصادر الرسمية لمزود الدفع، ويسجل ما هو موثق أو غير موثق أو محظور |
| `/wrap-up` | في نهاية المشاركة | يجمع النقاط المفتوحة، يوثق نتائج الوكلاء الفرعيين، وينتج ثلاثة مخرجات تحت `outputs/<engagement>/`: ملخص تنفيذ تنفيذي، ودليل تنفيذ تفصيلي موجه للكود، وقائمة تحقق للجاهزية للإطلاق |

كل ما يحدث بين `/start-session` و `/wrap-up` يُدار بشكل محادثاتي من قبل مدير المشاركة: إرشادات التنفيذ، أمثلة الكود، ومراجعات المتخصصين عند ظهور القرارات.

## كيف تعمل الجلسة

تمر المشاركة النموذجية بهذه المراحل بالترتيب:

1. **النطاق** : حالة الاستخدام، المكدس التقني، الأسواق، العملات، الجدول الزمني، حجم الفريق
2. **متطلبات أصحاب المصلحة** : مسؤول المدفوعات، الامتثال، مكافحة الاحتيال، الواجهة الخلفية، الواجهة الأمامية، البنية المعمارية، الأمن، المالية، تُجمع بشكل محادثاتي وتُحفظ كملفات مرجعية
3. **التحقق من السياق** : `/validate-context` يتحقق من الحقائق الخاصة بمزود الدفع ضمن النطاق مقابل المصادر الرسمية ويسجل العناصر الموثقة وغير الموثقة والمحظورة
4. **المدفوعات الأساسية** : Payment Intents، واجهة الدفع، معالجة التأكيد
5. **Webhooks** : معالجة الأحداث، تسوية حالة الطلبات، إعادة المحاولات
6. **مسارات المنصة** (إن كانت ضمن النطاق) : Connect، المدفوعات متعددة الأطراف
7. **المسارات الحضورية** (إن كانت ضمن النطاق) : Terminal، إدارة أجهزة القراءة
8. **إصدار البطاقات** (إن كان ضمن النطاق) : البطاقات المصدرة، ضوابط الإنفاق، التفويضات
9. **مراجعات المتخصصين** : كل وكيل فرعي يحمّل ملف متطلباته، يفحص القرارات ذات الصلة، وينتج نتيجة موافقة / تنبيه / حظر مع تبرير
10. **مخرجات المشاركة** : ملخص تنفيذ تنفيذي، ودليل تنفيذ تفصيلي موجه للكود، وقائمة تحقق للجاهزية للإطلاق لكل مشاركة

يقترح مدير المشاركة هذا التسلسل في البداية ويكيّفه وفقاً لما هو فعلياً ضمن نطاق فريقك.

## الوكلاء الفرعيون المتخصصون

ثمانية متخصصين متاحون للمراجعة متعددة الوظائف. يستدعيهم مدير المشاركة عند نقاط القرار المناسبة: لا تحتاج لاستدعائهم مباشرة.

| المتخصص | نطاق المراجعة |
|---|---|
| مسؤول المدفوعات | مراقبة مؤشرات الأداء، مخاطر الترحيل، الحوكمة التشغيلية |
| مسؤول الامتثال | نطاق PCI، SCA/3DS2، إقامة البيانات، مسار التدقيق |
| مسؤول مكافحة الاحتيال | قواعد المخاطر، استراتيجية 3DS، عملية النزاعات ورد المبالغ |
| مسؤول الأمن | إدارة الأسرار، التحقق من توقيعات Webhook، ضوابط مكافحة الاحتيال |
| مهندس الحلول | أنماط التكامل، أوضاع الفشل، قابلية التوسع |
| مطور الواجهة الأمامية | تجربة مستخدم الدفع، معالجة الأخطاء، إمكانية الوصول، التعريب |
| مطور الواجهة الخلفية | عدم التكرار، معالجة Webhooks، إعادة المحاولات، التسوية |
| المالية والخزينة | التسوية، تعدد العملات، المدفوعات، التقارير، الضرائب |

كل متخصص ينتج نتيجة: **موافقة**، **تنبيه** (المتابعة بشروط)، أو **حظر** (التوقف حتى الحل). يساعدك مدير المشاركة في حل التنبيهات والحظر قبل المتابعة.

## إضافة مزود دفع جديد

أنشئ مجلداً تحت `psps/<الاسم>/` مع ملف فهرس `README.md` وملف واحد لكل خط منتجات. اتبع نفس بنية `psps/stripe/`. لا حاجة لأي تغييرات في `CLAUDE.md` أو `sub-agents/`.
